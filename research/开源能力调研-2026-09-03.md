# 项目进化引擎Skill：开源能力调研

调研日期：2026-09-03。目标是在“代码整理修复大师”的基础上，找到能够补强已有项目理解、改动定位、新功能接入和新旧行为验证的开源能力。

本轮核对了仓库元数据、官方文档、目录和代表性 Skill/命令源码。下文的优先级与接入建议是基于这些材料的判断；尚未在实际业务项目中运行这些候选，也未安装或接入候选 Skill、插件、CLI、MCP。部分 GitHub API 请求失败的内容已用官方网页补充；未补充的部分明确保留为待核对项。

## 建议的组合

保留旧 Skill 的精准执行、模块职责与唯一规范来源、范围控制、证据有效性、修改前后验证。新增功能以用户的新需求为改动依据，不要求先证明旧实现存在缺陷。

第一批重点研究：

- cc-sdd：新需求与现有代码的差距、复用对象和接入位置。
- Agent OS：提取并按任务加载项目特有约定。
- Compound Engineering：有上下文的计划、把执行结果交还外层，以及保留有价值的解决经验。
- Superpowers：把改动细化到文件职责和可验证任务；与旧 Skill 重复的验证规则合并维护。
- Spec Miner：缺少文档时，从实际代码重建可追溯的项目认知。
- Understand Anything / CodeGraphContext：按需提供结构和依赖证据，作为工具增强。

主 Skill 保有需求解释、范围、授权与最终验收的责任。外部模块返回的报告、代码定位和影响判断都要与当前项目核对。

## 已核对的具体入口与接入条件

### cc-sdd

代表入口是 [kiro-validate-gap](https://github.com/gotalab/cc-sdd/blob/main/tools/cc-sdd/templates/agents/codex-skills/skills/kiro-validate-gap/SKILL.md)，搭配 [gap-analysis.md](https://github.com/gotalab/cc-sdd/blob/main/tools/cc-sdd/templates/shared/settings/rules/gap-analysis.md)。它会对应需求与现有模块，分析接入点、消费者兼容性，并比较扩展现有模块、新建模块、混合方案。

可借鉴的输出是：需求对应代码、缺失或未知能力、需要修改的位置、接口影响和建议方案。这些位置还需要由主 Skill 按当前代码核实。

当前仓库提供 Codex Skills 安装模式；旧的冒号命令与当前 Skills 模式不同。原始模板含有 `{{KIRO_DIR}}` 等占位符，并依赖规格、steering 和规则资源，不能只取一个 SKILL.md 就视为完整接入。可按[官方安装说明](https://github.com/gotalab/cc-sdd#quick-start)使用 `npx cc-sdd@latest --codex-skills` 生成所需文件；本轮未执行安装。

### Compound Engineering

已核对 [ce-plan](https://github.com/EveryInc/compound-engineering-plugin/blob/main/skills/ce-plan/SKILL.md)、[ce-work](https://github.com/EveryInc/compound-engineering-plugin/blob/main/skills/ce-work/SKILL.md) 和 [ce-compound](https://github.com/EveryInc/compound-engineering-plugin/blob/main/skills/ce-compound/SKILL.md)。

`ce-work` 明确提供 `mode:return-to-caller`：完成实现与本地验证后返回结构化结果，外层保有剩余审核与交付流程。它要求完整的 references 和执行资源，还可能产生实现提交；接入前要核对实际权限、工作区规则和返回协议。

`ce-compound` 只记录已经验证、且无法从最终代码与现有文档轻易恢复的重要经验。这适合防止“项目记忆”变成不断膨胀的重复说明。

### Superpowers

优先看 [writing-plans](https://github.com/obra/superpowers/blob/main/skills/writing-plans/SKILL.md) 的文件职责和任务规划，以及 [verification-before-completion](https://github.com/obra/superpowers/blob/main/skills/verification-before-completion/SKILL.md) 的结果证据要求。

整套流程带有 TDD、工作树、审查及其他技能之间的调用。提炼时应保留与本项目有关的决策方法，按用户的任务规模和已有授权决定工作深度。安装单个入口也要检查它引用的资源是否齐全。

### Agent OS

[Discover Standards](https://buildermethods.com/agent-os/discover-standards) 从代表性代码中提取项目独有规则及其原因；[Inject Standards](https://buildermethods.com/agent-os/inject-standards) 按当前任务读取相关约定，支持嵌入内容或引用标准文件。

这与“新功能遵循我的项目已有做法”直接相关。需要将当前观察、已确认约定和本次有意改变的规则区分开。它主要提供命令与标准文件；其他代理可读取底层 Markdown，接入方式见[官方说明](https://buildermethods.com/agent-os)。

### BMAD-METHOD

当前[既有项目指南](https://docs.bmad-method.org/existing-codebases/start-in-an-existing-codebase/) 使用 `bmad-build`、`bmad-spec`、`bmad-project-context`。旧资料中的部分工作流已被替代，不能直接按旧教程拼装。

可借鉴：小改动直接研究代码并构建；复杂更新再增加规格和规划；项目认知只补充必要且经过验证的上下文。完整调用要使用匹配版本的安装资源。许可证以[当前 LICENSE](https://github.com/bmad-code-org/BMAD-METHOD/blob/main/LICENSE)为准。

### GitHub Spec Kit

已读 [analyze.md](https://github.com/github/spec-kit/blob/main/templates/commands/analyze.md)：在任务生成后检查 spec、plan、tasks 的一致性、歧义、重复和遗漏。它能帮助建立“需求有没有落实到任务”的检查。

这类文档一致性仍需与实际代码接入和回归验证结合。原始命令模板依赖安装器替换和项目文件，接入前要检查模板生成、项目约束及扩展 hooks。

### Jeffallan：Spec Miner / Feature Forge

[Spec Miner](https://github.com/Jeffallan/claude-skills/blob/main/skills/spec-miner/SKILL.md) 追踪代码和数据流，要求观察具有代码位置、区分事实与推断，并记录不确定性。[Feature Forge](https://github.com/Jeffallan/claude-skills/blob/main/skills/feature-forge/SKILL.md) 面向新功能需求。

适用场景是接手缺少文档的项目，或某个旧功能难以解释。输出的“当前观察”应继续接受用户需求、既有规范和测试的判断，不能直接成为不可更改的业务规则。

目录登记的安装入口为 `npx skills add Jeffallan/claude-skills@spec-miner`；安装时应保留对应 references。本轮未安装。

### Understand Anything

[项目说明](https://github.com/Egonex-AI/Understand-Anything)提供 `understand`、`understand-explain`、`understand-diff` 等入口。

已读 [understand-diff](https://github.com/Egonex-AI/Understand-Anything/blob/main/understand-anything-plugin/skills/understand-diff/SKILL.md)：依赖项目图谱，检查图谱对应提交与当前变更，按改动查找相邻依赖并生成影响结果。该入口主要展开一跳关系，复杂链路仍需继续追踪。

它适合作为认知与影响线索。首次全量分析有上下文成本，后续可增量更新。直接调用需要相关插件运行资源和有效图谱，单独复制提示文件不等于完成接入。

### CodeGraphContext

已读配套 [SKILL.md](https://github.com/CodeGraphContext/CodeGraphContext/blob/main/.cursor/skills/codegraphcontext/SKILL.md) 和 [MCP 配置说明](https://github.com/CodeGraphContext/CodeGraphContext/blob/main/docs/docs/getting-started/mcp-setup.md)。

它提供本地索引、CLI 和 MCP 查询，能支持查找代码与分析代码关系。运行时接入需要匹配的语言解析支持、有效索引、统一的 CLI/MCP 配置和实际可用的工具入口。

关系查询用于缩小定位范围；新调用方、动态行为和运行时约束仍要通过当前代码与适当验证补充。

### Repomix

[Agent Skills Generation](https://github.com/yamadashy/repomix/blob/main/website/client/src/en/guide/agent-skills-generation.md) 提供 `--skill-generate`，可将本地或远端仓库整理成 Skill 形式的参考资料目录。官方将该生成能力标为实验性。

适合在蒸馏前整理外部实现与项目结构。接下来仍需筛选真正影响判断的规则，检查与旧 Skill 的重复和冲突，并验证提炼后行为。仓库内容的原始许可继续适用，打包不会改变它。

## 如何把“蒸馏”和“内部调用”落实到主 Skill

建议采用混合方式：

1. 将稳定的判断方法提炼到主 Skill 或按需读取的 references，并记录来源、版本、许可与改写范围。
2. 将专项能力作为条件调用：明确触发条件、输入、允许读取/修改的范围、需要返回的证据和停止条件。
3. 技能调用由执行代理读取实际可用的技能并执行；程序能力通过已配置的 CLI/MCP 接入。技能名称出现在文字中不等于相应工具已经可用。
4. 子模块的输出统一回到主 Skill：具体文件与符号、定位理由、影响关系、实现结果、验证证据和未覆盖部分。
5. 主 Skill 复核当前代码与新需求，处理冲突并决定是否完成。保护旧能力的同时，允许本次明确要求的行为变化。
6. 小更新只加载必要能力；较大更新才展开更完整的分析、图谱或执行编排。未接入外部依赖时，核心流程仍应能依靠现有搜索、阅读和验证能力工作。

正式蒸馏前，建议先选定一小组来源，固定其版本，在隔离示例项目上验证“定位正确、融入现有规则、保留指定旧行为”三个结果，再决定哪些外部依赖值得成为长期组成部分。
