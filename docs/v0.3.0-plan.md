# v0.3.0 实施与验收范围

本轮补齐上一轮明确留下的三项工作。完成状态必须对应可执行证据；继续保留 v0.1.0、v0.2.0 的原始结果。

## 1. 实际工具联调

- 固定 Serena 官方版本，在独立环境启动真实 MCP 服务；读取服务提供的工具说明和参数，确认项目，再查询定义与引用。
- 通过一次实际更新和一次代码整理修复大师的限定审核，验证更新目标、保留行为、范围与证据能传递给审核者，结果能返回主流程。
- 核对工作区变化后的引用和错误项目／不可用服务的处理。区分 stdio MCP 实测与宿主原生工具注册；不宣称未测试的接入方式。
- 可选依赖与核心分开，使用者已有的全局工具配置不作为试验修改对象。

## 2. 项目认知的增量刷新

- 在显式声明的目录与查询范围内，发现新增、修改、删除的证据和引用候选。
- 将变化传播到依赖这些证据的结论，同时保留不受影响的结论。
- 刷新后保留待核实状态；重复运行不能把未核实的结论自动变成有效。
- 重新确认必须绑定当时的文件状态，代码再次变化时拒绝使用过期确认。
- 工具输出引用候选和失效原因；语义判断与说明更新仍由实际阅读代码的代理完成。
- 测试新调用方、别名引用、删除、改名、依赖失效、无关修改、重复刷新、确认期间再次修改，以及只读和路径边界。

## 3. 扩大并重复对照评测

- 勘查 HTTPX 与 Datasette 的固定源码，选择跨模块且有现成回归入口的具体更新任务。
- 两个任务分别进行有／无 Skill 的两轮独立运行；相同代码、需求、工具、模型配置和环境，共八次实现。
- 任务、Skill、原始文件状态和独立验收在分发前固定；实现者不读取另一组或验收答案。
- 保留首轮失败和修复记录，核对真实补丁，独立执行行为与旧行为检查。
- 记录真实耗时、工具调用和运行时提供的 token 用量。没有证据的字段标为不可用，不估算成已测值。
- 单独记录专项工具联调，不将工具差异混入核心 Skill 对照结论。

## 4. 交付条件

- 包与工具测试通过；真实 MCP 联调、专项审核、认知刷新场景和八次试验均有结果与覆盖说明。
- README、验证记录、来源锁定和许可证与实现一致；发布包只包含运行所需的 Skill 资源。
- 推送后等待 Python 3.11／3.12 的 CI，通过安全安装器更新本地安装，再发布 v0.3.0。
- 若某项因实际能力边界无法完成，明确列为未完成；不能用文档说明或模拟调用替代真实验证。
